# Владельцу ByPass: ключ, подпись и выпуск обновлений

Эта инструкция позволяет самостоятельно выпустить официальную сборку на любом из двух ваших компьютеров. Обычным пользователям она не нужна: для них есть [инструкция по запуску](USAGE.md).

## Проще: помощник с кнопками

**На этом компьютере сейчас:**

1. В папке репозитория дважды нажмите **`owner.cmd`**. Откроется «ByPass — помощник владельца». Если помощник уже собран, можно открыть `tools/ByPass.Owner.exe` напрямую.
2. На вкладке «Ключ и перенос» нажмите **«1. Проверить ключ на этом компьютере»**. Ожидается подтверждение, что ключ подходит и тестовая подпись проверена.
3. Нажмите **«2. Создать резервную копию ключа…»**. Выберите Документы или флешку вне папки проекта. Придумайте пароль минимум из 16 символов и повторите его. Сохраните пароль в менеджере паролей отдельно от копии.
4. Нажмите **«3. Проверить резервную копию (без установки)…»**. Выберите только что сохранённый файл и введите тот же пароль. Если проверка прошла, файл исправен, пароль подходит и внутри ваш ключ. Текущий ключ при этой проверке не меняется.

**Вечером на втором компьютере:**

1. Получите актуальный официальный репозиторий — через свой Git-клиент или GitHub «Code» → «Download ZIP» с распаковкой. Для последующего выпуска нужен именно Git-checkout, а для одного импорта ключа достаточно распакованных исходников.
2. Перенесите зашифрованный `ByPass.key-backup.json` отдельно от пароля. Запустите `owner.cmd` под обычной Windows-учётной записью второго компьютера.
3. Нажмите **«4. Импортировать ключ на этом компьютере…»**, выберите файл и введите пароль.
4. Нажмите **«1. Проверить ключ»**. Успех означает, что второй компьютер может подписывать вашим ключом. Разные учётки Windows подходят.

Сегодня вы проверяете переносимый файл и подпись на первом компьютере. Проверка на втором компьютере завершает проверку реального переноса между учётными записями; первый компьютер её не заменяет.

Помощник не создаёт новый ключ и не заменяет существующий. Пароль вводится в окне, не передаётся в командной строке, не сохраняется в настройках или журнале. Работа с ключом не требует PowerShell 7; нужны Windows x64 и .NET Framework 4.8. `owner.cmd` собирает помощник системным компилятором .NET без скачивания дополнительных компонентов.

На вкладке **«Выпуск обновления»** есть проверка готовности и четыре кнопки по порядку: сборка с подписью автора → Defender → подпись обновления → публикация. Для этих операций нужны PowerShell 7, Git, чистый commit, push и успешный Actions, как описано ниже. Вводить команды сборки и подписи не требуется: помощник запускает имеющиеся скрипты и показывает результат. Только Defender запрашивает повышение прав; сама работа с ключом выполняется под вашей обычной учётной записью. Перед публикацией есть отдельное подтверждение.

Поле отпечатка сертификата Windows сейчас **оставьте пустым**. Оно понадобится, если получите настоящий сертификат Code Signing. Отпечаток задаётся для текущего запуска помощника; пароли сертификатов в нём не хранятся. Отдельный сертификат не нужен для уже работающей подписи ByPass.

Ниже сохранены подробности и команды для тех, кому удобнее терминал.

## 1. Что уже настроено

У проекта две разные подписи:

| Подпись | Что подтверждает | Состояние |
| --- | --- | --- |
| Собственный ключ ByPass | Авторство конкретных EXE/config, подлинность обновлений и каталога ядра | Уже работает |
| Сертификат издателя Windows (Authenticode) | Издателя EXE для Windows; нужен сертификат с доверенной цепочкой | Поддержка подготовлена, сертификата пока нет |

Закрытый ключ ByPass уже создан. **Не запускайте `initialize-signing.ps1` заново и не создавайте другой ключ на втором компьютере.** Установленные приложения доверяют существующему открытому ключу.

Локальный закрытый ключ находится здесь:

```text
%LOCALAPPDATA%\ByPass\Signing\release.key
```

Он зашифрован для вашей Windows-учётной записи и защищён правами доступа. Простое копирование `release.key` на другой компьютер не работает: используйте экспорт и импорт ниже.

В GitHub находятся только открытый ключ, подписанные подтверждения, исходники скриптов и эта инструкция. Они не позволяют подписывать чужие сборки вашим ключом. Сам закрытый ключ, его резервная копия, пароль и будущий PFX сертификата **не должны попадать в Git или GitHub Actions**.

Официальный отпечаток открытого ключа ByPass, SHA-256:

```text
813c22d95ae9b8e82d7776a5c8c87acb47c05bf3d0cfa6137ceeeb915b4e125f
```

## 2. Подготовьте компьютер

Нужны Windows 10/11 x64, .NET Framework 4.8, Git и **PowerShell 7**. Открывайте PowerShell 7 (`pwsh`), обычно без прав администратора, под своей Windows-учётной записью. Нужен интернет и работающий Microsoft Defender для проверки релиза.

На текущем компьютере перейдите в папку проекта:

```powershell
Set-Location 'E:\AllGit\discord\discord_obhod_app'
$PSVersionTable.PSVersion
git --version
git status --short
```

На втором компьютере сначала склонируйте официальный репозиторий в удобную папку:

```powershell
git clone https://github.com/xxXdemidXxx/discord_obhod_app.git
Set-Location discord_obhod_app
```

Все команды дальше выполняются **из корня проекта**. В командах Git авторизуйтесь своим аккаунтом GitHub, которому разрешён push в этот репозиторий. Скрипт публикации использует эту же Git-авторизацию; отдельный токен в файл записывать не нужно.

## 3. Сделайте резервную копию ключа — один раз на первом компьютере

Резервная копия ещё не создана автоматически: для неё вы сами выбираете пароль. Сохраните длинный уникальный пароль в менеджере паролей; минимум — 16 символов.

```powershell
./tools/export-signing-key.ps1 -Destination "$env:USERPROFILE\Documents\ByPass.key-backup.json"
```

Введите пароль, затем повторите его. Символы при вводе не показываются. **Не вставляйте пароль в команду или переписку.** Скрипт сохранит только зашифрованный файл, не выгружая незашифрованный ключ на диск. Папка Documents должна существовать; при необходимости выберите другую существующую папку вне репозитория.

Сохраните зашифрованный файл отдельно от пароля. Не коммитьте его, не прикладывайте к релизам и не пересылайте вместе с паролем. Защита резервной копии: AES-256-CBC, HMAC-SHA256 и PBKDF2-SHA256 с 310 000 итераций. Существующие резервные копии скрипт не перезаписывает.

## 4. Настройте второй компьютер — один раз

Перенесите зашифрованный `ByPass.key-backup.json` на второй компьютер своим безопасным способом. Например, положите его в Documents. Пароль получите отдельно из своего менеджера паролей.

В PowerShell 7 из корня склонированного проекта выполните:

```powershell
./tools/import-signing-key.ps1 -Source "$env:USERPROFILE\Documents\ByPass.key-backup.json"
```

Введите пароль. Скрипт проверит, что это ключ именно ByPass, и сохранит его зашифрованным для Windows-учётной записи второго компьютера. Теперь оба компьютера используют **один и тот же ключ**. Импорт не перезаписывает уже существующий локальный ключ.

На втором компьютере проверьте доступность ключа без вывода его содержимого:

```powershell
Test-Path "$env:LOCALAPPDATA\ByPass\Signing\release.key"
```

Ожидается `True`. Подпись при упаковке также проверяет соответствие ключа проекту. Сам файл `release.key` не открывайте и никуда не отправляйте.

## 5. Выпустите новую версию — повторяется при каждом обновлении

### Получите последние изменения

```powershell
git switch main
git status --short
git pull --ff-only
```

Если `git status --short` показывает ваши незавершённые изменения, сначала разберитесь с ними. Не сбрасывайте их ради выпуска. На двух компьютерах всегда сначала получайте актуальный `main`.

### Измените программу и номер версии

После текущей 0.5.2 следующая версия, например, 0.5.3. В `src/Version.cs` измените:

```csharp
public const string Value = "0.5.3.0";
```

Обновите номер в `README.md` и `TESTING-GUIDE.txt`. В `RELEASE-NOTES.md` укажите новую версию, опишите изменения понятными словами и исправьте имя совместимого архива внизу на `Obhod-0.5.3-win-x64.zip`.

Для замены иконки используйте `assets/bear_icon.png`, затем выполните `./tools/make-icon.ps1`: он обновит `assets/ByPass.ico`. Сохраняйте в commit оба файла.

### Проверьте изменения и отправьте исходники

```powershell
./test.ps1
git diff
git status --short
```

Тесты должны закончиться успешно. Просмотрите изменения и добавьте только нужные файлы проекта. Пример для выпуска, в котором поменялись лишь номер версии и документация:

```powershell
git add src/Version.cs README.md TESTING-GUIDE.txt RELEASE-NOTES.md
git commit -m "Release ByPass 0.5.3"
git push origin main
```

Если меняли код или иконку, добавьте и соответствующие файлы. **Не добавляйте ключи, резервные копии и сертификаты.** После commit команда `git status --short` должна ничего не вывести.

Откройте [GitHub Actions проекта](https://github.com/xxXdemidXxx/discord_obhod_app/actions). Дождитесь зелёного результата workflow **Build, test and release** именно для отправленного commit. Он проверяет код и пакет, запускает Defender и создаёт **черновик релиза**. CI не получает ваш закрытый ключ и самостоятельно не публикует официальный выпуск.

### Соберите и подпишите авторство локально

На одном из компьютеров с импортированным ключом, из чистого checkout отправленного commit:

```powershell
./package-friends.ps1 -OwnerSignature
```

Скрипт сам собирает программу и создаёт в `releases`:

- `ByPass-win-x64.zip` — архив для пользователей;
- `Obhod-0.5.3-win-x64.zip` — архив для обновляторов старых версий;
- `build-proof.json` — подпись автора, также вложенная в оба архива;
- `update-unsigned.json` — пока неподписанные метаданные обновления.

Распакуйте **новый ZIP в отдельную папку** и проверьте программу: значок, надпись о подтверждённой подписи автора, обычный запуск, отказ и подтверждение запроса Windows, подключение, смену стратегии и выход. Автотесты не запускают настоящий драйвер и не заменяют эту проверку. Настоящие повышенные права должны быть у помощника ядра, а окно обычно работает с правами пользователя.

### Проверьте пакеты антивирусом

```powershell
./tools/scan-release.ps1
```

Для выпуска нужны работающий Defender, базы не старше 48 часов и успешный результат проверки обоих архивов и распакованной программы. Скрипт создаёт `security-report.json` и `defender-scan.log`.

Если требуется повышение прав, откройте PowerShell 7 **от администратора**, перейдите в ту же папку проекта и выполните только эту команду сканирования. Для подписи вернитесь в обычное окно своей учётной записи. Если базы устарели, обновите их в «Безопасность Windows» → «Защита от вирусов и угроз» → обновление защиты и повторите проверку. При обнаружении угрозы сначала устраните причину; скрипт не публикует такой пакет.

### Подпишите обновление и опубликуйте

```powershell
./tools/sign-release.ps1
./tools/publish-release.ps1
```

Первая команда создаст подписанный `update.json`. Вторая проверит подпись, commit, хеши, свежесть отчёта и успешный workflow, загрузит локальные файлы в черновик и опубликует его.

После упаковки не меняйте EXE, config, ZIP, подтверждения или отчёт. Если что-либо изменили, повторите упаковку, сканирование и подпись. Отчёт перед подписью и публикацией должен быть не старше 24 часов.

Готовый результат появится на [странице релизов](https://github.com/xxXdemidXxx/discord_obhod_app/releases). [Постоянная ссылка скачивания](https://github.com/xxXdemidXxx/discord_obhod_app/releases/latest/download/ByPass-win-x64.zip) начнёт отдавать новую версию. В приложении появится предложение обновить оболочку, установка потребует согласия пользователя.

Опубликованный релиз неизменяемый. Если после публикации обнаружили ошибку, увеличьте номер и выпустите следующую версию. Не перезаписывайте старый тег.

## 6. Независимо проверьте официальную сборку

Скачайте и распакуйте опубликованный ZIP. Из **официального checkout проекта** выполните, подставив путь к распакованному EXE:

```powershell
./tools/verify-build.ps1 -Executable 'C:\ByPass\ByPass.exe'
```

Рядом должны лежать `ByPass.exe.config` и `build-proof.json`. При успехе скрипт напечатает `Verified ByPass`, версию, автора `xxXdemidXxx`, commit и официальный отпечаток ключа.

Такая проверка не запускает скачанный EXE. Надпись в окне сама по себе не является внешним доказательством: в переписанной чужой программе можно нарисовать любую отметку. Скрипт проверяет настоящую подпись и хеши файлов.

## 7. Подключите сертификат Windows, когда он появится

Для имеющейся защиты ByPass сертификат покупать не требуется. Это отдельный шаг, чтобы подписывать EXE для Windows. Нужен настоящий сертификат **Code Signing** с доверенной цепочкой и доступным закрытым ключом.

Текущий скрипт работает с сертификатом в хранилище вашей Windows-учётной записи `Cert:\CurrentUser\My`. Установите сертификат и необходимые компоненты по инструкции своего поставщика. Если используется облачный сервис подписи, для него потребуется отдельная интеграция: текущий скрипт не подключает такой сервис автоматически.

Если поставщик выдал PFX, его можно импортировать в PowerShell 7:

```powershell
$certificatePassword = Read-Host 'Пароль PFX' -AsSecureString
Import-PfxCertificate -FilePath 'C:\Private\publisher.pfx' -CertStoreLocation Cert:\CurrentUser\My -Password $certificatePassword
Remove-Variable certificatePassword
```

Подставьте свой путь. PFX и его пароль не храните в репозитории. На другом компьютере сертификат настраивается отдельно по правилам поставщика; резервная копия ключа ByPass его не содержит.

Найдите отпечаток своего сертификата:

```powershell
Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
    Select-Object Subject, Thumbprint, NotAfter, HasPrivateKey
```

В том же окне PowerShell **до упаковки** задайте отпечаток без пробелов:

```powershell
$env:BYPASS_SIGNING_THUMBPRINT = 'ВСТАВЬТЕ_40_СИМВОЛОВ_ОТПЕЧАТКА'
./package-friends.ps1 -OwnerSignature
```

Дальше выполните обычные сканирование, `sign-release.ps1` и `publish-release.ps1`. Отпечаток не секрет; переменная в этой команде действует для текущего процесса и дочерних процессов. В новом окне задайте её снова.

Скрипт проверяет срок сертификата, назначение Code Signing, закрытый ключ и доверенную цепочку, подписывает помощник перед встраиванием в оболочку, затем саму оболочку и добавляет отметку времени. Ошибка подписи останавливает сборку.

Проверка EXE после сборки, например для 0.5.3:

```powershell
Get-AuthenticodeSignature './dist/ByPass-0.5.3.exe' |
    Select-Object Status, SignerCertificate, TimeStamperCertificate
Get-AuthenticodeSignature './dist/ByPass.EngineHost.exe' |
    Select-Object Status, SignerCertificate, TimeStamperCertificate
```

Ожидается `Valid` и заполненные сертификаты издателя и отметки времени. Пока сертификат не настроен, `NotSigned` здесь нормально: собственная подпись ByPass проверяется отдельно через `verify-build.ps1`. Доверенный сертификат не гарантирует отсутствия предупреждений SmartScreen или срабатываний антивирусов.

## 8. Если процесс остановился

| Сообщение или ситуация | Что делать |
| --- | --- |
| Закрытый ключ не найден | На первом компьютере проверьте свою Windows-учётную запись; на втором импортируйте резервную копию |
| Локальный ключ уже существует | Импорт повторно не нужен; не удаляйте существующий ключ без выяснения причины |
| Пароль резервной копии неверен | Возьмите сохранённый пароль из менеджера; пароль восстановить из файла нельзя |
| Требуется чистый checkout | Сделайте commit нужных изменений; не подписывайте незакоммиченные исходники |
| Workflow ещё не прошёл | Дождитесь результата Actions для этого commit; при ошибке откройте журнал и исправьте причину |
| Черновик не найден | Убедитесь, что успешен и этап `draft` workflow и что номер версии увеличен |
| Отчёт проверки отсутствует или устарел | Повторите `scan-release.ps1`, затем `sign-release.ps1` |
| Файлы изменились после подписи | Повторите упаковку, сканирование и подпись; не редактируйте хеши вручную |
| Релиз уже опубликован | Для исправления нужна новая версия |
| Нет сертификата Windows | Выпускайте с собственным ключом ByPass; издатель Windows пока не подтверждён |

Если оба компьютера и резервная копия потеряны, старый ключ восстановить нельзя. Для нового ключа потребуется отдельный план перехода установленных приложений. Если ключ или пароль украдены, обычное повторное создание файла не исправляет доверие старых версий.

При обычном обновлении оболочки не меняйте `security/update-public.xml` и `security/engine-trust.json`. Обновление доверенного ядра требует отдельной проверки и подписания каталога; порядок и ограничения описаны в [DEVELOPMENT.md](DEVELOPMENT.md). Детали защиты — в [SECURITY.md](SECURITY.md).
