# Разработка и публикация

[На главную](README.md) · [Инструкция пользователя](USAGE.md)

Владельцу сборки: [пошаговая настройка подписи и выпуск релиза](OWNER-GUIDE.md).

Для работы с ключом без терминала откройте `owner.cmd`: графический помощник позволяет проверить ключ, создать и проверить переносимую зашифрованную копию, импортировать её на втором компьютере. Вкладка выпуска запускает те же проверенные скрипты сборки, Defender, подписи и публикации. Исходники помощника находятся в `tools/OwnerAssistant.cs` и `tools/OwnerKeyStore.cs`; в пользовательский ZIP они не входят. Совместимость с резервными копиями PowerShell проверяется в обе стороны.

ByPass написан на C# / WinForms для Windows 10/11 x64 и .NET Framework 4.8. NuGet не используется; сборка выполняется системным компилятором .NET Framework.

## Сборка и проверка

Запускайте PowerShell 7 из корня репозитория:

```powershell
./fetch-engine.ps1
./build.ps1
./test.ps1
./package-friends.ps1
```

- `fetch-engine.ps1` скачивает официальное ядро 1.10.3 и проверяет закреплённый SHA-256.
- `build.ps1` создаёт `dist/ByPass-<версия>.exe` и config, а также совместимую копию `Obhod-<версия>.exe`. Отдельно собирает минимальный помощник ядра и встраивает его в EXE вместе с открытым ключом и каталогом доверия. Для запуска нужна папка `data` с ядром и настройками.
- `test.ps1` проверяет приложение без запуска настоящего драйвера. Сам скрипт при необходимости скачивает архив ядра. С `-Network` дополнительно выполняются реальные GitHub и HTTPS-запросы.
- `package-friends.ps1` создаёт готовый архив с EXE, config, стандартными настройками, официальным ядром, инструкцией и лицензиями. Исходники оболочки, тесты, скрипты сборки, личные списки и журналы в него не попадают. BAT-файлы и утилиты из официального ядра сохраняются: оболочка читает стратегии из BAT как данные.
- `prepare.ps1` импортирует локальное ядро 1.10.2 и официальное 1.10.3 для разработки, сохраняя настройки. Путь локального ядра можно передать параметром `-LocalEngine`.

Тесты охватывают разбор стратегий, Windows-кавычки, владение процессом, ZIP traversal, сохранение/откат, полный автоподбор, подтверждение победителя, отмену, DNS/TLS, метаданные релизов и замену EXE. Снимки окна сохраняются в `tests/window*.png`.

## Файлы релиза

| Файл | Назначение |
| --- | --- |
| `ByPass-win-x64.zip` | Готовая программа по постоянной ссылке для пользователей |
| `ByPass-win-x64.zip.sha256.txt` | SHA-256 пользовательского архива |
| `Obhod-<версия>-win-x64.zip` | Совместимый пакет для обновляторов старых версий |
| `Obhod-<версия>-win-x64.zip.sha256.txt` | SHA-256 архива |
| `update.json` | Подписанные метаданные и хеши оболочки; создаётся локально после проверки |
| `security-report.json` | Результат Defender с версиями баз, временем и хешами пакетов |
| `build-proof.json` | Подпись автора для конкретных EXE и config, включена в официальные ZIP |

Пользовательский архив содержит папку `ByPass` и `ByPass.exe`. Совместимый архив сохраняет расположение `Obhod/Obhod.exe`, которое требуют старые обновляторы. EXE и config в обоих архивах побайтово одинаковы; пути внутри ZIP отличаются, поэтому SHA-256 архивов различается.

Внутреннее имя .NET-сборки `Obhod-<версия>`, пространство имён и mutex сохраняются для совместимости. Название продукта Windows, окно, трей и новый ярлык используют ByPass. Обновление заменяет EXE по прежнему пути: у старой установки имя файла может остаться Obhod.exe, а интерфейс станет ByPass.

Постоянная ссылка для README и распространения:

```text
https://github.com/xxXdemidXxx/discord_obhod_app/releases/latest/download/ByPass-win-x64.zip
```

`update.json` продолжает ссылаться на архив с номером версии: установленные версии 0.3/0.4 принимают только такое имя. Новый обновлятор принимает оба имени, проверяя независимую подпись RSA-3072, точный адрес репозитория и тега, размер, SHA-256 архива и подписанные хеши EXE/config. При отсутствии подписи не переходит к неподписанному GitHub API. Не удаляйте архив с номером версии, пока нужна совместимость со старыми приложениями.

Доверенный сертификат издателя пока отсутствует. Независимая подпись обновления и каталог ядра уже используются; подключение настоящего сертификата описано ниже. Заменяются только EXE и config; пользовательские данные и версии ядра остаются на месте.

## Публикация новой версии

Для выпуска через агента есть единый `release.ps1`; правила одинаковы для Codex (`AGENTS.md`) и Claude (`CLAUDE.md`). Сохранённый чистый commit можно выпустить командой `./release.ps1`. Для правок без commit укажите `-CommitMessage` и `-Files` с явным списком проверенных исходников. Сценарий сам выполнит все проверки, push, подпись и публикацию, включая ожидание CI и проверку публичных файлов. Закрытый ключ используется только локально; графический помощник не требуется. Пример полного поручения — в [OWNER-GUIDE.md](OWNER-GUIDE.md).

Ручной порядок отдельных шагов:

1. Увеличьте `AppVersion.Value` в `src/Version.cs`, например после 0.5.3 до `0.5.4.0`, обновите документацию и `RELEASE-NOTES.md`.
2. Выполните `./test.ps1`, сделайте commit и push. Workflow проверит этот commit, просканирует пакет и подготовит черновик релиза. Actions закреплены полными SHA; сборка имеет только `contents: read`, запись разрешена отдельному заданию черновика.
3. Дождитесь успешного workflow. На компьютере владельца с локальным ключом, из чистого checkout этого commit, выполните:

```powershell
./package-friends.ps1 -OwnerSignature
./tools/scan-release.ps1
./tools/sign-release.ps1
./tools/publish-release.ps1
```

Если локальный Defender требует повышенных прав, выполните только сканирование в PowerShell администратора. Ключ подписи хранится в профиле владельца; сборку и подпись выполняйте из этого профиля. Публикация использует существующую Git-авторизацию GitHub в памяти, не записывая токен на диск. Для сканирования нужны работающий Defender и базы не старше 48 часов; для подписи нужен успешный отчёт не старше 24 часов.

`package-friends.ps1` создаёт `update-unsigned.json`. Подпись генерирует `update.json`, оставляя прежние поля для обновляторов 0.3/0.4 и добавляя подписанную полезную нагрузку. Новые клиенты читают только подписанные поля. Пакеты содержат commit исходников; изменённый checkout не допускается к подписи. Публикация проверяет подпись, отчёт, хеши, успешный workflow и тег именно этого commit. Публичный релиз никогда не перезаписывается. Последняя стабильная ссылка остаётся прежней до публикации подписанного выпуска.

Закрытый ключ RSA-3072 хранится в `%LOCALAPPDATA%\ByPass\Signing\release.key`, зашифрован DPAPI CurrentUser и закрыт ACL. В репозитории и Actions его нет. Он уже создан: **не запускайте инициализацию повторно**. Другой разработчик может собирать и проверять код, но не подписывать выпуск. Правила резервирования и ограничения — [SECURITY.md](SECURITY.md).

Каталог `security/engine-trust.json` подписан этим же ключом. `tools/approve-engine.ps1` допускает только закреплённый архив 1.10.3 и сверяет неизменяемые файлы с его содержимым. Для другого ядра сначала отдельно проверьте происхождение архива, бинарные файлы и стратегии, обновите закреплённые данные, затем подпишите новый каталог и выпустите оболочку. Не заменяйте проверку каталогом хешей из произвольной локальной папки или только ответом GitHub API.

### Сертификат издателя Windows

Когда появится настоящий сертификат подписи кода с доверенной цепочкой и закрытым ключом, установите его в `Cert:\CurrentUser\My` и задайте:

```powershell
$env:BYPASS_SIGNING_THUMBPRINT = '40-символьный отпечаток без пробелов'
./package-friends.ps1
```

`tools/sign-executable.ps1` проверит срок, закрытый ключ, EKU Code Signing и доверенную цепочку. Сначала подписывается помощник, затем он встраивается в оболочку и подписывается сама оболочка; используется SHA-256 и сервер отметки времени. При любой ошибке сборка прекращается. После подписи снова нужны сканирование и подпись update.json: байты EXE уже изменились. Сертификат не передаётся в Actions. Без отпечатка EXE остаются неподписанными. Самоподписанный сертификат не создаётся. Доверенная подпись не гарантирует мгновенного исчезновения предупреждений SmartScreen.

При запуске выполняется только проверка обновлений. Уведомления оболочки и ядра отображаются в окне на всех вкладках и могут быть скрыты до следующего запуска. Скачивание начинается после нажатия «Обновить» и отдельного подтверждения «Да / Нет» с выбором «Нет» по умолчанию. Обновление ядра требует остановить обход; обновление оболочки восстанавливает подключение после перезапуска.

## Один ключ на двух компьютерах

Оба компьютера должны использовать один и тот же закрытый ключ. Новый ключ на втором компьютере создавать не нужно.

На первом компьютере, в PowerShell 7:

```powershell
./tools/export-signing-key.ps1 -Destination "$env:USERPROFILE\Documents\ByPass.key-backup.json"
```

Скрипт дважды попросит пароль скрытым вводом. Используйте длинный уникальный пароль из менеджера паролей (не менее 16 символов). Файл защищён AES-256-CBC + HMAC-SHA256 с отдельными ключами, полученными через PBKDF2-SHA256 (310 000 итераций). Пароль не передаётся в аргументах команды и не пишется в файл. Незашифрованный ключ на диск не экспортируется. Репозиторий как место для резервной копии запрещён.

Перенесите только зашифрованный файл на второй компьютер своим безопасным способом, пароль держите отдельно. Там склонируйте официальный репозиторий и выполните:

```powershell
./tools/import-signing-key.ps1 -Source "$env:USERPROFILE\Documents\ByPass.key-backup.json"
```

После ввода пароля скрипт проверит соответствие официальному открытому ключу и сохранит закрытый ключ, снова зашифрованный DPAPI уже второй Windows-учётной записи, с ограниченным ACL. Существующий локальный ключ не перезаписывается. Оба компьютера смогут подписывать ваши сборки. Потеря одного компьютера не требует смены ключа, если он не скомпрометирован; при компрометации нужна отдельная миграция доверия.

## Отметка автора сборки

`package-friends.ps1 -OwnerSignature` подписывает квитанцию `build-proof.json` для конкретных EXE/config, автора `xxXdemidXxx`, версии и commit. Она находится внутри ZIP и отдельным файлом релиза. Обычная сборка CI или чужого checkout не получает такой подписи. После проверки внизу окна появляется отметка подтверждённой сборки. Старые обновляторы не копируют квитанцию; 0.5.1 получает её по точному тегу своей версии, проверяет подпись и хеши, затем сохраняет. Без сети и квитанции отображается «Подпись автора не подтверждена».

Для внешней проверки без запуска проверяемого EXE используйте скрипт из **официального репозитория**, а не из чужой сборки:

```powershell
./tools/verify-build.ps1 -Executable 'C:\ByPass\ByPass.exe'
```

Открытый ключ закреплён отпечатком SHA-256 `813c22d95ae9b8e82d7776a5c8c87acb47c05bf3d0cfa6137ceeeb915b4e125f`. Подделать подпись для этого ключа без закрытого ключа нельзя. Любую надпись в окне переписанной программы скопировать можно; для независимого подтверждения используйте проверку подписи или будущую подпись Windows доверенным сертификатом. Публичный репозиторий разрешает форки и предложения изменений, но прямой push в ваш репозиторий доступен только владельцу и тем, кому вы сами дали права.
## Ручная проверка привилегированного запуска

Автотесты проверяют подписи, подмену ядра/стратегий/DLL, отказ от неподписанных обновлений, перенос ключа, реальный локальный канал и идентификацию процессов, чтение под токеном пользователя, замену/откат оболочки и интерфейс. Для тестов владения процессом используется безопасная заглушка; настоящий драйвер не запускается, UAC не подтверждается автоматически.

Перед распространением в своей сети проверьте обычный запуск установленного ZIP: отметку автора, отказ UAC, повторный запуск с подтверждением, переключение стратегий, выход и прекращение своего winws. В диспетчере задач окно должно иметь обычные права, а ByPass.EngineHost.exe — повышенные; winws должен работать из `%ProgramData%\ByPass\runtime-*\bin`. После завершения окна или помощника этот процесс должен остановиться. Это проверяет реальный драйвер и запрос Windows, которые автотесты намеренно не запускают.
Совместимость со старой 0.4.4 проверяется её сохранённым исходным обновлятором (commit 53325e4): он скачивает новый архив, создаёт прежние файлы staging и запускает новый помощник. Помощник получает update.json и build-proof.json по точному тегу собственной версии и проверяет подписи и хеши до сигнала готовности. Отдельно проверяются подмена EXE/config с пересчитанными старыми хешами и сохранность установленной программы при отказе.
